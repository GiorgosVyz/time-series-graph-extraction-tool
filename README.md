# Time Series Digitizer & Forecaster

A local Streamlit tool for recovering clean single-color line charts and evaluating forecasts with expanding-window rolling-origin validation.

## Run

Use Python 3.11 or newer. From this directory:

```sh
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
python -m pip install -r requirements.txt
python generate_samples.py
python -m streamlit run app.py
python -m pytest -q
```

The app uses a single page: choose **Upload** for your own chart or **Demo** for Trend, Wave, or Level shift. It opens in Upload mode, with pixel-coordinate controls collapsed. Plot boundaries and the dominant saturated curve color are suggested when an image is loaded. Check the green border and contrasting recovered points; adjust coordinates and color if necessary. Recovered data and forecasts appear automatically as soon as the axis values and extraction settings are valid. Changes update the results immediately; incomplete or invalid settings hide the results until corrected. Review the displayed axis ranges and extraction points against your chart. A loading indicator appears while forecasts are evaluated, and cached backtests avoid unnecessary refitting. Uploaded charts automatically read numeric or supported temporal x-axis labels and numeric y-axis labels using local OCR. Values are filled when the detected labels form a consistent linear scale; unreadable fields remain editable. Each new image resets calibration to avoid carrying values over from another chart.

**Download forecast** saves a self-contained interactive HTML chart containing both recovered history and future predictions. Open it in a browser, including offline. Numerical forecasts remain available via **Download forecast data (CSV)**; recovered observations and rolling backtest results also export as CSV. Forecast controls update interactively; cached backtests avoid refitting when only the error tolerance changes.

## Architecture and methodology

`extraction.py` first looks for four supported plot borders. For open charts it uses aligned, regularly spaced horizontal gridlines together with a colored curve spanning the plot. Header rules and volume regions are filtered using geometry and color evidence. Curve color is selected by horizontal coverage and saturation; tracing prefers pixels close to the saturated stroke rather than the pale shaded fill. The widest connected stroke anchors the trace, short marker gaps are interpolated, and large gaps or poor coverage are rejected. Linear calibration reverses the downward pixel y-axis. Detection remains a suggestion: complex layouts, colored volume bars, large occlusions or multiple panels may require manual correction. The local OCR calibration module is described below.

`forecasting.py` provides **ETS**, **ARIMA**, a **Naive** last-value baseline, and an **Auto** selection option. ETS is the default: additive errors, damped additive trend, no seasonality (ETS(A,Ad,N)), with estimated initialization. It replaces the separate Holt option. ARIMA tests only (1,0,0), (1,1,0), and (0,1,1); the stationary model includes a constant, while differenced models have no drift. At every origin, order selection uses a holdout of 2–5 observations from the end of that training prefix (one fifth of its length, within those limits). Candidates are ranked by inner-holdout MAE and refitted on the complete training prefix in that order. No outer-validation or future observations participate in order selection. ARIMA requires at least 12 training observations as a practical guard, not a guarantee of sufficient evidence. Optimizer iterations are capped, nonconverged/nonfinite candidates are rejected, and an error is reported if no candidate can be fitted. This is a restricted model comparison, not a comprehensive automatic ARIMA search. Constant series use the constant forecast directly. At each origin only the historical prefix is fitted; every complete validation fold predicts the same horizon. Errors are actual minus predicted. Headline MAE, RMSE and failure rates compare the selected model and naive baseline at the requested terminal lead time, using identical validation origins. A detail table reports each intermediate lead time, with a histogram of terminal errors. Fewer than 20 origins triggers a limited-evidence notice; 20 is a UI heuristic, not a statistical sufficiency guarantee. No automatic model selection is performed using future values.

**Auto** uses only the first **Initial training points** to select a base model. It compares the requested terminal lead time at up to five recent common rolling origins wholly inside that earlier prefix. If that prefix contains at least 12 training points plus the horizon, all three models are eligible and use the same origins with at least 12 training points. Otherwise ETS and Naive are compared from at least four training points, with ARIMA marked unavailable. A candidate failing any selection fold is excluded rather than scored on fewer, different folds. Lowest historical failure rate wins; ties use lower MAE, then the simpler model (Naive, ETS, ARIMA). The small selection window bounds computation; it is limited evidence rather than a comprehensive model search.

The selected model stays fixed while later observations provide the headline rolling backtest. Outer origins start at **Initial training points**, so none of their target values participated in selection. The final forecast refits that same selected base model on the complete recovered history. Auto needs at least four training points plus one horizon inside its selection prefix and another horizon afterwards, or `2 * horizon + 4` points overall. Selection results and exclusions are shown in an expander, separately from later evaluation scores. Its table uses **Selection failure rate**, **Failures** and **Selection tests**; the Auto headline and later evaluation tables use **Backtest failure rate**. The later caption reports failures and forecast count explicitly. These periods can have different rates: for example, the supplied one-month image has 0/5 selection failures but 21/46 later failures (45.7%) at horizon 5 and a 5% tolerance. Under the former 5-unit tolerance the same Naive backtest had 13/46 failures (28.3%); changing the tolerance definition changes the score. The earlier score is not a guarantee of later performance. Candidate errors and matching actual values are cached independently of tolerance, so threshold changes rerank without refitting them; a changed winner may require its own later backtest. If the winner fails later, the error is reported rather than choosing a different model using those evaluation outcomes. Direct `predict` and `backtest` accept base models; the app composes `compare_models`, `select_best_model`, and the later base-model backtest for Auto.

The UI, HTML chart and forecast/backtest CSVs identify the chosen model. Backtest CSVs preserve unit errors and add signed `error_percent`, `failed` and `tolerance_percent`; Auto exports also identify `selection_tolerance_percent`. Auto CSVs include `forecast_method`, `selected_model`, and `selection_points`. Auto remains optional; ETS stays the default. The selection applies to the extracted series, including any interpolated samples, and does not establish a future probability of success.

**Failure tolerance (%)** defaults to 10. Each forecast fails when `100 * abs(actual - prediction) / abs(actual)` exceeds the tolerance; it uses that forecast’s actual value, not the first value, prediction or series range. The boundaries are included, with only floating-point roundoff allowed. For an actual value of 60, ±10% permits 54–66. Negative actuals use their absolute magnitude in the denominator. At an actual value of zero, an exact match is assigned 0% error; any nonzero miss is treated as an unbounded percentage error and counts as a failure. `summarize(errors, tolerance, actuals)` requires matching actual values for this percentage rule. MAE and RMSE stay in the original value units. The histogram uses signed percentage errors, keeps the same overestimate/within/underestimate colors, and shows tolerance lines in percent. Unbounded errors remain in failure-rate counts but are excluded from the histogram with an explicit annotation. Percentage errors can be unstable near zero; see the [scikit-learn discussion](https://scikit-learn.org/stable/modules/generated/sklearn.metrics.mean_absolute_percentage_error.html). The observed proportion estimates historical failure probability for each lead time. It cannot determine an exact probability for a future forecast. Overlapping folds share observations and errors are dependent; small counts and distribution shifts reduce reliability. Extraction error is not quantified by forecast backtesting. Prediction intervals are deferred until a separate calibration/coverage evaluation can be implemented.

## Automatic axis calibration

`calibration.py` uses RapidOCR and ONNX Runtime locally. Numeric words are selected by their positions along the bottom and either the left or right value axis. Conflicting left/right scales require manual selection of values. Decimal points, decimal commas, signed numbers, scientific notation, and explicit grouped prices such as `7,800.00` and `7.800,00` are supported. A comma followed by exactly three digits is treated as grouping; check ambiguous locale formats. A consensus fit requires at least three consistent ticks spanning half the axis and rejects inconsistent scales. OCR box offsets near endpoints are snapped to observed ticks or their lattice. This remains a suggestion: check the displayed values and overlay, particularly for unusual layouts. Logarithmic axes, rotated labels and unrecognized locale formats are unsupported.

First use downloads roughly 30 MB of OCR weights into `work/ocr_models/`; subsequent use runs offline. Models are not committed to Git. Only model files are downloaded; chart images are never sent to an OCR service. Install the updated requirements in the same environment used to run Streamlit. If OCR or model download fails, the app retains manual entry.

## Supported inputs and limitations

Clean, single, continuous colored curves with a linear value axis and a numeric or supported temporal x-axis. At least five extraction points are required. Crop out legends and other curves. Black curves, disconnected traces, logarithmic axes, uncertainty bands and multiple series are unsupported. Original sampling frequency cannot generally be identified from a raster image. The app automatically suggests a count from clearly separated, similarly sized, evenly spaced filled point markers spanning the plot, or from dense unit-spaced integer indices / dense regularly spaced temporal labels. Marker evidence takes priority over tick counts and can work even when OCR is unavailable. It assumes each original observation has a marker; charts that show markers only on selected points may undercount. Suggestions remain editable; manual corrections persist until a different image is loaded. Editing a calculated daily count switches to custom sampling; selecting Daily again resumes automatic date-based calculation. The label-based fallback assumes one observation per visible label and must be checked; sparse ticks do not establish the original sample count. **Extraction points** preserves a suggested original count when available. For date-only charts with an unknown count, it defaults to daily interpolation: `(end date - start date).days + 1`, including both endpoints. This is recalculated for each image and when either date changes; it is not a fixed count. Other unknown counts retain the editable 100-sample fallback. The caption explicitly states when the original count is unknown. Choosing another count also marks the result as sampled data; it does not establish an original count. Changing the count updates the extraction and forecast automatically. Oversampling creates artificial data. In sampled mode the overview says “sampled points,” the forecast chart and evaluation are labelled as sampled data, and a notice explains that interpolation can make backtest errors appear smaller. The evaluation measures the resampled curve rather than original unseen observations. Synthetic shift charts interpolate steep segments and therefore incur raster uncertainty. The image itself stays local to the application process.

## Time axes and series overview

`time_axis.py` recognizes English weekdays (including the common “Wen” variant), short/full month names, 24-hour and AM/PM clock labels, month/day labels without a year (such as `Oct 21`), and dates with an explicit year. ISO dates such as `2026-10-25` are preferred; named dates such as `25 Oct 2026` are also accepted. Month/year ticks such as `Jun 2026` are calibrated at the start of the month; intermediate endpoints are approximate and marked as estimated. The time-axis selector and start/end fields allow correction. Numeric-axis behavior is preserved.

Weekdays, month names and month/day labels retain their labels without inventing a calendar year. Clock, weekday, and month rollovers are unwrapped only when at least three labels fit a consistent linear progression. Historical midnight or cycle crossings are marked, for example `00:30 (+1 day)`, `Mon (+1 week)`, and `Jan (+1 year)`. Calendar dates retain their explicit year. Ambiguous numeric dates (`03/04`) and timezone changes are not inferred automatically. Month/day labels use relative coordinates; no actual year is assigned, and precise elapsed calendar duration is not claimed. For nonuniform visible calendar labels, interpolation uses the recognized label positions rather than discarding a legitimate date as a linear-fit outlier. Unlabelled endpoints remain approximate. A relative leap-year template is used internally only to encode month/day positions, including Feb 29, without exporting that template year.

**Sampling frequency** distinguishes **Unknown**, **Daily**, and **Intraday**. Date-only charts with no detected original count select Daily automatically and show “Daily sampling · interpolated.” These are calendar-day samples, including weekends, not recovered exchange sessions. Yearless month axes remain Unknown because their calendar year and month lengths are not available. Visible clock labels suggest Intraday without assuming an hourly interval. Clock displays omit generated seconds unless seconds are present in the recognized or edited labels; start/end times between visible ticks are marked approximate. Calendar labels show dates only unless Intraday is selected and actual time labels are available. Hours and minutes produced by interpolating month/year ticks are hidden. Changing frequency updates the labels and results automatically; each new image resets it. Daily periods requiring fewer than five points cannot be forecast. Counts above the existing 300-point forecasting limit are displayed correctly, but forecasts pause until the period is shortened or a smaller custom count is chosen.

Temporal forecasts use `Observation +1`, etc., or `Daily observation +1` for confirmed daily sampling. These labels are consistent in chart ticks, hover text, HTML and CSV downloads. Future positions are drawn with regular spacing for readability; exact future calendar dates, intraday timestamps, exchange sessions and holidays are not inferred. Sampled temporal series use `Sample +1`, etc., even when the source chart is daily: a sampled step does not establish an original trading session. In calendar-day sampling its interpolation interval is one day. Numeric-axis forecasts continue their numeric spacing.

Recognized labels appear in chart ticks, hover values, the interactive HTML export, and recovered/forecast CSVs. Backtest CSVs include forecast-origin and target labels. For sampled series, recovered, forecast and backtest CSVs also include `sampling_basis=sampled_curve` and `extraction_points`; daily interpolation also adds `sampling_interval=calendar_day`. The downloaded HTML chart identifies the sampled point count. The values used to fit forecasting models remain the recovered numeric observations.

The **Series overview** shows the observation count and readable period, followed by **Estimated high**, **Estimated low**, and **Overall change**. Approximate calendar periods are marked, without generated hours and minutes. A note about first occurrences appears only for repeated extrema. Constant series are described without claiming a trend. It is generated directly from extracted values, uses no language-model API and makes no causal or statistical-significance claims. Dense tick labels may still represent fewer points than the original series; check the suggested observation count before interpreting the overview.

Four additional upload examples and their known values are in `tests/fixtures/time_axes/`: weekdays, months, hours crossing midnight, and ISO dates. All four were verified with the real local OCR engine through upload, extraction, overview and forecasting. Additional intraday, one-month and five-day screenshots in `tests/fixtures/market/` cover faint grids, AM/PM labels, yearless dates, partial curves and nonuniform label spacing.

## Simple financial area charts

Open charts with a single saturated price line, pale area fill, left/right numeric scales, and sparse month labels are supported. Gray volume bars, current-price badges, and small point markers are excluded where possible. The preview uses blue recovered points on a red curve, and red points on other curves, for visibility. A trace preview is shown even when some axis values await correction.

Sparse month labels do not determine the original sample count, trading calendar, or exact endpoints. With month/year dates and no detected original count, the application calculates one interpolated sample per calendar day from the displayed start/end dates. Yearless month charts retain the 100-sample fallback. This is a chosen extraction resolution, not an estimate of the original number of observations or a count inferred from image width. Values are sampled from the recovered curve. Nonuniform calendar label positions are preserved, and explicit daily interpolation uses a daily time grid rather than forcing equal pixel spacing. This does not recover missing source timestamps or identify the original sample count. Yearless month labels retain relative month positions (including editable fractional-month offsets); month/year labels provide an approximate calendar period. Faint grids retry a lower edge threshold. The longest panel line helps distinguish gridlines from shorter fill edges. When an intraday curve ends before the horizontal axis, extraction stops at the available curve rather than extending a flat line through empty space. Candlesticks, multiple price curves, logarithmic scales and substantial occlusions remain outside scope. No exchange, holiday or session calendar is implemented.

The user-supplied screenshots in `tests/fixtures/market/` are regression examples, not datasets with complete source ground truth. The earlier left/right-area examples were checked with real OCR and 40 explicitly specified samples. Intraday and yearless month/day formats use the labelled 100-point sampling fallback. Endpoint checks were close to the visible price labels; full-series accuracy is not claimed. A separate synthetic shaded chart with known values tests extraction MAE below 1.5 units, including headers and gray volume bars.

## Validation and samples

`generate_samples.py` reproducibly creates three PNG charts and original CSV data: trend, wave, and level shift. All use plot rectangle (60,30,660,330), time 0–59, values 0–100 and 60 observations. Tests compare extracted values with ground truth (MAE below one value unit), check border/color suggestions, short and constant ETS series, ARIMA minimum training size and fitting failures, rolling alignment, prefix invariance for ETS, ARIMA and Naive after changing future observations, metric calculations and invalid inputs. The app also displays sample extraction MAE when the sample axes and observation count are used.

Streamlit interaction tests exercise startup, eight-observation inputs, model switching, invalid-calibration recovery, image switching, empty uploads, automatic upload results, updates after calibration edits, and automatic recovery after invalid or missing values are corrected. Temporal checks cover daily date precision, approximate periods, intraday source evidence, forecast labels in charts and CSVs, and frequency changes/reset. Marker-count tests cover 5/20/40-point charts, missing or irregular markers, unmarked financial lines, uploads with unavailable OCR, and user corrections. Sampling checks cover dynamic daily counts on the full CRWV screenshot, different periods and leap years, preservation of detected counts, edited counts, image resets, sampled-series labels and export metadata. Auto checks cover failure-rate/MAE ranking, ties, common selection origins, training-prefix boundaries, unavailable and failed candidates, short series, exported selection metadata, tolerance changes without refitting selection candidates, the exact monthly-chart selection-versus-backtest distinction, and relative-tolerance behavior across value scales, negative/zero actuals, boundary roundoff, Auto ranking and percentage histograms. These tests need local loopback sockets. Verified locally: **175 tests passed**, on Python 3.13 with Streamlit 1.66.1 and Statsmodels 0.15.0. This is functional validation, not a guarantee for arbitrary chart styles.
